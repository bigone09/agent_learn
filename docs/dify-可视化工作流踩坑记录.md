# Dify 可视化工作流踩坑记录

搭建「数据整理 → LLM 生成 ECharts JSON → 代码节点清洗 → 渲染」数据分析智能体过程中的实战结论。

## 应用类型选择

- **渲染 ECharts 必须用对话流（Chatflow）的「直接回复」节点**。工作流（Workflow）只有「结束」节点，不渲染 markdown/ECharts，只会输出 JSON 文本。
- 两种应用类型不能直接互转，需新建对话流，但可照搬已调通的节点。

## 图表渲染

- 「直接回复」节点里用 ` ```echarts ... ``` ` 代码块包裹 ECharts option JSON 触发渲染（Dify 官方推荐方式）。
- ECharts 是前端渲染，不受沙箱字体限制，中文标签可直接用（区别于沙箱内 matplotlib 缺 CJK 字体会变豆腐块）。
- 节点 Test Run 面板永远只显示变量原始值，不渲染图表；要在实际聊天/预览界面看渲染结果。

## LLM 输出清洗

- **代码执行节点做"清洗"不做"执行"**：LLM 输出的 ECharts JSON 常带 markdown 围栏/单引号/思考残渣，用 `json.loads` + `ast.literal_eval` 兜底清洗即可。不建议 `exec` 动态执行绘图代码——dify-sandbox 大概率禁 `exec`，且 matplotlib 产出接不进渲染节点。
- **DeepSeek reasoner 默认把思维链塞进 `text` 字段**（带 `<!--dify-deepseek-reasoning-->` 标记），`reasoning_content` 反而为空。解法：LLM 节点开「启用推理标签分离」或换 deepseek-chat，否则思考过程污染下游解析。

## 输出顺序控制

- Chatflow 的「直接回复」节点**到达即输出**，并行分支中两个 Answer 的输出顺序不可控——处理链路短的分支总是先到。
- 需要固定输出顺序时，把输出动作放到同一执行线：串行排列，或并行计算后在汇合点用变量聚合统一输出。
- 多个直接回复节点的输出会拼进**同一条助手消息**，翻历史时整段文本重新解析。

## 历史消息图表加载失败（Chart loading… 卡住）

- 现象：实时对话中图表正常，查看历史消息时 ECharts 组件永久转圈。
- 原因：流式输出是分段增量解析，图表段到达时后文还没来；历史回读是整条消息重新解析，分析文本里的反引号（LLM 爱写 ` ``` ` 代码块）会破坏 echarts 围栏配对，JSON 解析失败。
- 解法：分析文本输出前用代码节点清洗反引号（`re.sub(r'`+', '', text)`），或提示词禁止 LLM 使用代码块；围栏本身写在 Answer 模板里，代码节点只输出纯 JSON。

## 数据传递

- **数据整理节点要传完整数据**给 LLM；若只传"列名+类型+前五行样例+总行数"摘要，图表只能画前几个实体。
- 沙箱出口被 Dify 的 ssrf_proxy 强制接管，无法直连宿主机/局域网 IP，只能访问 docker 网内地址（数据库容器需加网络别名）。

## 运维备忘

- 容器重启后插件运行时是懒加载的，启动后 1 分钟内切换模型可能报"网络服务错误"（plugin runtime not found），等十几秒重试即可。
- 容器重建后需恢复沙箱依赖（pip install）与容器网络别名。
